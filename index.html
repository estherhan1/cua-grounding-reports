ScreenSpot-Pro: does giving a GUI-grounding agent tools help?

Qwen3-VL-8B-Instruct on all 1581 ScreenSpot-Pro examples. Every example is shown with the ground-truth box, both arms' predicted clicks, all 4 runs' raw outputs, and the tool agent's full trajectory.

New: Deep Research + GUI hard-task report — SURMOUNT-4 evidence verification, FIFA U-17 research, Serper/live diagnostics, and no-search controls.
Complete experiment archive. Browse the full OSWorld, OSWorld-G, and ScreenSpot-Pro report set, including the master A1–A7 / B / C / D table and all per-example traces: open all experiments.
Headline. Giving the agent a 10-tool kit costs 76 net rows (133 fixed, 209 broken; McNemar χ²=16.4, p=5.0e-05). Decomposing that loss: −74 of it is the handoff itself — the agent delegates to GTA1-7B, a weaker grounder than the base model it replaces. Everything the tool loop adds on top of that handoff — multi-call reasoning, an instruction-rewriting stage, an 8152-character tool policy — is worth net −2 rows, p=0.95. 98% of GTA1 calls are issued before the agent has looked at the screenshot, so the rewrites it produces are guesswork.

Which tools did the agent actually use?

The tool arm had a 10-tool kit available. Over 1581 examples it made 1763 calls (1.12 per example); every single example called at least one tool, so nothing here is explained by the agent declining to use them.

Almost the whole kit went unused. 94.3% of all calls were to the one grounding specialist, and 95.3% of examples called only that. So “giving the agent tools” was in practice “routing grounding to GTA1” — which is exactly why the loss decomposes into −74 for the handoff and −2 for everything else.

Why the search-tool line was closed

A separate experiment, and the one negative result worth reading in full: letting the instruction-refiner search the web before rewriting. Both arms rewrite and hand the grounder "{original} ({rewrite})"; they differ only in whether the refiner may call search. Baseline here is the plain-rewrite arm at 51.80%, not raw GTA1 — scoring against GTA1 would credit search with the plain rewrite's gain.

runplain rewrite+ searchfixedbrokenetMcNemar p
original saved run51.80%49.78%5991-320.011
independent re-run (logs tool responses)51.80%50.60%6786-190.146

Cite this as consistently negative in direction across runs, significant in the original full-pool run — not as “replicated at p<0.05”, because the cleanest re-run is p=0.15. The re-run loses less because it removes two damage sources the original had (untagged text reaching the grounder, and second-tool escalation).

What the report overturns. The recorded explanation was “web knowledge overrides correct screenshot perception”. It fails its own paired control: the plain arm invents UI labels more often than the search arm (40.0% vs 32.6%), so the largest failure category is a property of the rewriter, not of search. What search actually adds is churn — it doubles the flip rate (16.3% vs 6.4%, p<0.0001) without shifting which way rows flip (p=0.41). And the entire loss sits on small targets: break rate 34.0% on sub-40px targets, falling to ~5% above 120px; icon −2.81pp vs text −0.20pp.

Another benchmark: WebArena-812 — agent execution, not grounding

Separate line of work, included here because it shares the harness. A3-Qwen3.5-9B (McGill-NLP) run on all 812 WebArena tasks against a self-hosted site stack, scored with BrowserGym's own evaluators. This measures whether an agent can complete a task, not whether it can point at the right pixel, so none of the numbers above are comparable to it.

Headline. 45.44% (369/812), ±3.42pp against the leaderboard's 42.1 for the same model on the same 812-task split. That is inside the confidence interval, so read it as reproduced, not beaten — and the run deviates from the reference protocol in one way that plausibly accounts for the gap: the site stack was never reset between tasks.
